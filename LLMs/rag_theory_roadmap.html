Embeddings — what to study
  • What a vector is — a list of floats representing meaning in N-dimensional space
  • How Word2Vec / BERT introduced contextual embeddings (similar meaning = nearby vectors)
  • Embedding dimensions — why 768-dim vs 3072-dim matters for quality vs cost
  • How embedding models differ: sentence-transformers vs OpenAI vs BGE
  • Why the same word can have different embeddings in different contexts
Similarity search — what to study
  • Cosine similarity — measures angle between vectors, range [-1, 1], ignores magnitude
  • Dot product — faster, good when vectors are normalized (same as cosine then)
  • Euclidean (L2) — measures absolute distance, sensitive to vector magnitude
  • When to use which: cosine for text semantic search, L2 for image embeddings
  • Why "top-k" retrieval works: get the k closest vectors to query
Tokenization & context — what to study
  • What a token is — roughly 0.75 words; "unbelievable" = ~3 tokens
  • Context window — maximum tokens a model can process at once
  • Why chunking exists — embedding models have their own token limit (512, 8192)
  • Overlap: why you repeat 10-15% of tokens between chunks (avoid cutting mid-thought)
  • Tiktoken / HuggingFace tokenizers — how to count tokens before chunking

Fixed-size chunking — what to study
  • RecursiveCharacterTextSplitter in LangChain — splits on \n\n, \n, space, char in order
  • chunk_size (tokens) and chunk_overlap — typical: 512 size, 50 overlap
  • Problem: can split mid-sentence or mid-table — loses context
  • When to still use it: fast prototyping, uniform prose documents
Semantic / structural chunking — what to study
  • MarkdownHeaderTextSplitter — splits on #, ##, ### to preserve section boundaries
  • Sentence-level splitting — NLTK, spaCy sentence tokenizers
  • Semantic similarity chunking — embed sentences, split when cosine distance drops
  • Why this matters for financial reports: each section has a distinct topic
  • LlamaIndex MarkdownNodeParser — preserves heading hierarchy as metadata
Hierarchical chunking — what to study
  • Core idea: store both small chunks (for precise retrieval) and large chunks (for context)
  • Small child chunk retrieved by similarity → its parent chunk sent to LLM
  • LlamaIndex ParentDocumentRetriever and HierarchicalNodeParser
  • Why this beats plain large chunks: retrieval is precise, but LLM gets full context
  • Typical setup: 128-token child chunks, 512-token parent chunks

How vector DBs work — what to study
  • A vector DB stores (id, vector, payload) — payload = metadata like page, section, type
  • At insert: vector is indexed using HNSW or IVF structure for fast ANN search
  • At query: your query vector is embedded → DB finds k nearest neighbors
  • Qdrant collections, points, payloads — understand this data model
  • Metadata filtering: filter by type="table" AND page > 10 before vector search
Indexing algorithms — what to study
  • Flat / brute-force: exact search, compares every vector — only for small datasets
  • IVF (Inverted File): clusters vectors, only searches relevant clusters — faster, slight recall loss
  • HNSW (Hierarchical Navigable Small World): graph-based, very fast, high recall, default in most DBs
  • ANN (Approximate Nearest Neighbor) vs exact: ANN trades ~1% recall for 100x speed
  • ef_construction, m parameters in HNSW — build quality vs memory tradeoff
Hybrid search — what to study
  • Dense search: embedding similarity — good for semantic/paraphrased queries
  • Sparse search (BM25/TF-IDF): keyword matching — good for exact terms like "revenue 2024"
  • Why hybrid wins for financial docs: "Q3 EBITDA" needs both keyword + context match
  • Reciprocal Rank Fusion (RRF): merges ranked lists from both searches mathematically
  • Qdrant supports sparse+dense natively; BGE-M3 produces both in one model pass

RAG pipeline — what to study
  • Index time: chunk → embed → store in vector DB (runs once, or on doc update)
  • Query time: embed query → retrieve chunks → assemble prompt → LLM generates answer
  • Naive RAG vs Advanced RAG vs Modular RAG — evolution of the pattern
  • Grounding: why RAG reduces hallucination (model answers from retrieved evidence)
  • The role of metadata at retrieval: filter by doc, page, section before similarity search
Retrieval strategies — what to study
  • Top-k: retrieve k most similar chunks, simple baseline (k=3 to 10)
  • MMR (Maximal Marginal Relevance): balances relevance + diversity, avoids redundant chunks
  • Reranking: use a cross-encoder (slower but precise) to re-score top-50 → pick top-5
  • Cross-encoder vs bi-encoder: bi-encoder fast at retrieval, cross-encoder precise at reranking
  • Cohere Rerank, BGE-Reranker — popular reranking models
Context assembly — what to study
  • Context window budget: LLM has N tokens total — retrieved chunks consume most of it
  • Prompt structure: system prompt + retrieved context + user query + output format
  • Lost-in-the-middle problem: LLMs attend more to start/end of context, miss middle chunks
  • Context compression: summarize retrieved chunks before inserting (LLMLingua, etc.)
  • Citation: how to attribute final answer back to source chunks (page, section, doc)

Table representation — what to study
  • Why raw markdown tables embed poorly: embeddings treat "|" as noise, not structure
  • Linearization: convert table rows to "In 2024, Revenue was €60.1B, up 2% YoY"
  • NL summary + raw table storage: embed the summary, store full table in payload
  • Structured JSON approach: store table as JSON in Qdrant payload for exact lookup
  • Table-specific embeddings: some models fine-tuned on structured data (TAPAS, etc.)
VLM + RAG — what to study
  • VLM (Vision Language Model) converts chart/image to text description
  • That text is then embedded just like any other chunk
  • image_path stored in payload — returned at retrieval so chatbot can display the image
  • Multi-vector approach: embed both the VLM text AND (optionally) a CLIP image embedding
  • ColPali: newer approach — embed PDF page as image directly, skip OCR/VLM pipeline
Metadata design — what to study
  • Every point in vector DB needs: source, page, section, type, chunk_id
  • type field (text | table | image) enables filtered retrieval: "only search tables"
  • Payload filtering in Qdrant: filter BEFORE similarity search, not after
  • Sparse metadata (exact match) vs dense vectors (semantic) — when to use each
  • Namespace / collection separation: separate collection per doc vs mixed with metadata filter
